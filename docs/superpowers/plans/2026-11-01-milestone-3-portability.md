# Milestone 3 portability implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Preview and import supported legacy or portable records without losing text, provenance or deletion history, then reopen and export those records accurately.

**Architecture:** Pure bounded adapters feed encrypted, expiring server previews. A transport chunk is not necessarily a complete dependency group: P1 must prove bounded assembly before P2 freezes persistence. Explicit selection publishes each complete group atomically using owner-scoped typed aliases and durable tombstones; status reconciles interruptions without guessing whether records were created. Use existing reading, export, erasure and recovery services.

**Tech Stack:** Node 26, TypeScript, Zod, React, Hono, D1/R2, Vitest/workerd and Playwright; existing dependencies only.

**Spec:** [Milestone 3 preparation](../../MILESTONE_3_PREPARATION.md), [migration specification](../../architecture/ASSETS_AND_MIGRATION.md), [import design](../../design/legacy-imports.md). Reviewed 2026-11-02. P1 pure foundations are implemented locally; persistent workflows remain unimplemented; enum membership and disposable reference checks do not establish native-format support. D8 identifies the transport/group contract that still needs an executable proof before P2.

## Global Constraints

- Required adapters: `reflection-import.v1`, `reflection-export.v1`, documented `tarot-json`, and bounded inspected Patternlike 0.7.0/0.8.0 variants. Native `pixel-json` returns `422 IMPORT_INVALID` until separately verified; no invented exporter, field mapping or live account access.
- `ImportSource.namespaceId` is a dataset UUID, `revision` its explicit source revision. Filenames, chunks and export ticket IDs never define identity. Ownership always comes from authentication.
- Maximum serialized request body: 2 MiB; preserve the existing 200,000 UTF-16-code-unit document ceiling unless D8 explicitly revises the owning contract. Maximum normalized legacy record plus exact original JSON: 192 KiB UTF-8. Count JSON escaping/envelope bytes separately from decoded document length; never truncate to fit. Retain the 256 KiB limit on unrelated routes.
- Maximum 100 items per current preview, expiring after 24 hours; current commit accepts 1–100 unique indices in 0–99. These are not established maximum family sizes. Export at most 100 records and 1 MiB per page with a ticket lasting at most 60 minutes; unsaved-record retention can shorten it. Records never split across export pages or lines. D8 must define references to groups spanning multiple bounded previews.
- Apply the 20 MiB account cap including encrypted bytes and at least 1 KiB per owned row. Import at capacity fails atomically for the affected dependency group; read/export/delete remain usable.
- Preserve full legacy questions up to 10,000 characters, generated text up to 30,000, authored statements within existing bounds, exact original timestamps and nullable normalized dates. History uses the 500-character preview and `questionTruncated`; exact reopening uses full content.
- Imported grants, permissions and generation receipts are historical metadata, never restored authority. Do not import credentials, keys, entitlements, location or private profile fields as application state.
- All new private copies require encryption/AAD, accounting, export, erasure, rekey and restore coverage. Complete these before exposing preview/commit creation. Extend the traversal/guard patterns from [Continuity C2](2026-11-01-milestone-3-continuity.md#c2--complete-grantpreview-and-private-copy-lifecycle-support) for import families; C2 itself does not depend on P2 being finished.
- Preserve exact Reflection colors, local Newsreader/Figtree/Outfit typography, shared components and Paper/Evening behavior. Keep private import contents in memory; no browser storage, URL, logs or telemetry.
- Preserve dirty work. Reserve `0019_import_workflows.sql` after the continuity migration only if needed and still available; do not edit applied migrations or assume numbers survive parallel development.

## Review Focus

1. Same records arrive through overlapping exports/chunks, with changed whitespace or changed content: duplicates must be distinguished from conflicts using exact documented identities/content. Pin in P1/P2.
2. An erased target has multiple aliases or a missing parent: deletion must retain a content-free tombstone and cannot be bypassed by changing only source revision. Pin in P2/P4.
3. Invalid UTF-8, surrogate boundaries, malformed NDJSON, oversized data or hostile markup: bounded rejection or inert text, never partial parsing, silent truncation or executable content. Pin in P1/P3.
4. Commit acknowledgement is lost after some dependency groups succeed: status/resume must preserve completed groups and avoid duplicate records or guessed parent links. Pin in P2/P3.
5. Restored historical metadata grants access or leaves a copied raw record alive: imports must confer no live permission, and erasure/rekey must cover all surviving copies. Pin in P2/P4.

## File boundaries

`src/domain/imports/types.ts` owns normalized internal records; `parse.ts` performs bounded adapter dispatch; `identity.ts` constructs canonical keyed-identity inputs. `src/worker/readings/imports.ts` owns preview, commit and reconciliation with the existing database services. `src/client/imports.tsx` and `imported-reading.tsx` own review and inert rendering. Existing `checks/check-imports.ts` remains a reference check, not a substitute for tests of those services.

New signatures below are proposed implementation interfaces. `ImportWrite` means `z.infer<typeof apiSchemas.ImportWrite>` and `ImportCommit` means `z.infer<typeof apiSchemas.ImportCommit>`; other schema names similarly use their existing inferred types. Runtime service methods use the authenticated Worker `Session`. Any extension required by D8 must be declared in these source schemas and regenerated projections before persistence implementation.

## Transport and group proof required in P1

### Frozen selection and cancellation boundaries — 2026-11-02

Tarot's selectable units are the base reading, each nonblank entry reflection, each card's authored reflection and each follow-up turn. A selected base reading excludes `reflections`, card `userReflection` fields and `followUps`. A turn excludes its `journalContext`; that context can contain other unselected readings. Nested units use stable identities/JSON pointers from the complete source before chunking. Dependencies remain explicit; selecting a child never silently selects its parent.

The retained raw representation is an explicitly labelled `selected-fields.v1` projection: exact lexical JSON spans for the unit's allowed fields, with nested independent units omitted. Its SHA-256 describes that projection, not the original enclosing object. Leaf note values preserve their exact JSON token. The whole upload and enclosing parent object are never persisted as raw provenance. Unsupported private fields fail validation rather than being silently retained. Missing source information stays unknown.

Each projected legacy raw copy has exactly one unit owner. Native portable provenance can contain explicit context copies, which retain their additional C2/P2 erasure dependencies. P2 must index preview, staging, committed-body and alias copies by that identity; deleting a child removes every such copy even when the parent survives, with backup replay using the same identity. P1 tests selection and redaction projections; actual encrypted/database erasure is a P2 acceptance requirement and cannot be claimed from those pure tests.

Commit execution accepts **one complete group per client submission**, identified by a manifest hash over its ordered selected units. Staging may span bounded previews; a commit cannot enqueue another group. Cancellation stops the client from submitting the next group. Once a group has been submitted, reconcile its durable status until the outcome is known; neither aborting HTTP nor cancelling the client loop promises rollback. P1 tests cancellation between groups and during the submitted group's reconciliation; P2 must prove the same boundary with real transactions. No durable multi-group cancellation queue is introduced.

The existing limits are not yet a complete upload protocol. One valid export page can exceed the import document ceiling, an account export can contain multiple `ImportSource` identities, and one session can have more than 100 portable records because notes retain revisions. An existing account fixture must prove all three cases; a small Tarot fixture is insufficient.

P1 must specify the canonical chunk carrier and bounded group manifest, with stable source identities, explicit completeness/dependencies and owner-scoped references between previews. Measure the serialized request after escaping. Preserve exact raw record spans when rechunking; parsing then `JSON.stringify` is not lexical preservation. The client may stream/repack complete records but must not pretend a transport fragment is an unchanged original export page or invent cursor order.

P2 must demonstrate atomic visibility of the complete selected group within actual D1 transaction limits. If one batch cannot hold it, stage invisible owned records and publish through an atomic completeness/fence check, with cleanup, accounting and erasure covering the staging rows. That changes the older “one batch per group” implementation assumption and requires an explicit schema/API revision in this plan; do not hide it behind partial success. Independent complete groups may still succeed separately. No new user permission is needed to resolve this technical design within the agreed scope.
