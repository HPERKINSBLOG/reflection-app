`src/contracts/astrology.ts` now owns native birth, calculation, chapter and Pattern schemas. Migration `0021_astrology_pattern.sql` adds a separate native Pattern edition mode and astrology basis without inventing a tarot generation request. The live reading union includes Pattern while the v1 export schema remains frozen. Local profile/preview/save routes use the existing encrypted owner, revision, accounting, erasure and rekey services. Production activation is closed.

The journal remains a saved-reading collection. `HistoryItem.method` and server-side method filtering are implemented before pagination. Imports are explicitly labeled Imported, including historical astrology snapshots; labels never confer native calculation or tarot follow-up authority. Standalone notes, full-text/date search and activity-sort metadata are still absent.

## Implementation order

1. **Foundation and exact first-slice plan:** completed in this phase. [Engine/timezone decision and evidence](../architecture/ASTROLOGY_FOUNDATION.md), [design](../superpowers/specs/2026-11-05-your-pattern-design.md), [task checklist](../superpowers/plans/2026-11-05-your-pattern.md).
2. **Your Pattern end to end:** implemented for local preview on desktop and mobile, with real calculated placements and retained originals. Complete the independent numerical, exact-catalogue editorial and hosted resource gates before enabling it in a hosted environment.
3. **Broader shared-journal implementation:** standalone notes, full-text search, date/activity ordering and the remaining Figma presentation. These are tracked gaps; a limited method filter does not close them.
4. **Timing:** qualified transit/event engine, phases and linked notes.
5. **Time Travel:** date comparisons and new revisit context with the original reading retained.

The current task does not require redrawing completed Figma flows. Implementation should add targeted states only when real validation reveals a missing interaction, such as a daylight-saving occurrence chooser.
